# MIM0 – Accessing data

**Our claim: Svada-mini follows MIM0 (self-assessed). No requirement has the status "Not followed". Requirement R3.1 does not apply to our use case (see below).**

How the statuses work is explained in [How Svada-mini follows the MIMs](README.md). The text of MIM0 is from MIMs v9.0 as we read it on 2026-10-28
(<https://mims.oascities.org/mims-specification-v9.0/accessing-data>); see the version caveats in the overview. MIM0 helps with how data can be accessed
once data sets are discovered and agreements are in place. It has no conformance test.

In Svada-mini data is reached in three places: the **open view** (Distribution B as a web page and JSON, on the chamber view's address), the
**time series interface** for Distribution B (NGSI-LD temporal queries), and the **City's gateway** for Distribution A, which needs an approved
agreement. The data first travels between the provider and the City over the Dataspace Protocol and is not "accessed" by users in this sense.

## Capabilities and requirements

### C1 – Machine-readable data is retrievable through the web

| Req. | What it says | Status | What we do, and what is missing |
|---|---|---|---|
| R1.1 | Data can be retrieved in at least one machine-readable format; the format may be chosen by HTTP content negotiation. | **Followed** | The open view answers JSON to `Accept: application/json` (or `?format=json`) and HTML to a browser, at the same address. The time series interface answers NGSI-LD JSON. Shown with real responses in `docs/07-folj-ett-varde.md`; we have no dedicated automated test of the content negotiation. |
| R1.2 | Data is retrievable through at least one standard web-based mechanism. | **Followed** | HTTPS and REST on the open view; the ETSI NGSI-LD API (temporal) for the time series. |
| R1.3 | Access mechanisms are formally described. | **Followed** | The open view has an OpenAPI 3.1 description at `/openapi.json` (it describes the data interface: `/brunnar`, `/brunnar/{id}` and `/health`; the draft data model pages under `/modell` describe themselves and are not in it) on the chamber view's address (`publik_vy_fel.py` checks that it matches the service's allowlist and holds no internal detail). The time series interface is the standard ETSI NGSI-LD temporal API (ETSI GS CIM 009); we restrict it to Distribution B and to a fixed set of parameters, which the proxy configuration lists (`services/caddy/Caddyfile`, the block for the time series address). The interactive API pages generated by the framework are switched off on public addresses on purpose. |
| R1.4 | (*should*) The data models used by payloads should be specified. | **Followed** | The models are specified in prose (`docs/14-dataprodukten.md`) and, for the open view, in the OpenAPI description. The draft model is also published as machine-readable files (JSON Schema, JSON-LD context, term list) under `/modell` and referenced from `conformsTo`; that is a MIM2 matter (its R1, which we follow); see [MIM2](mim2-representing-data.md). |

### C2 – Access is structured and queryable

| Req. | What it says | Status | What we do, and what is missing |
|---|---|---|---|
| R2.1 | Data is provided through a structured, consistent interface. | **Followed** | NGSI-LD entities with fixed attributes; the open view's JSON has a fixed shape described in the OpenAPI document. |
| R2.2 | The system supports basic querying and/or filtering, for example by time, location or attributes. | **Followed** | The time series interface filters by time (`timerel`, `timeAt`, `endTimeAt`, `lastN`) and by attribute (`attrs`), with `limit` and `offset`. The open view lists the latest day per chamber and gives one chamber's series. Filtering by location is not offered for Distribution B: B has no positions by design (information class K0R1T1), so there is nothing to filter. The gateway for Distribution A passes NGSI-LD queries through; we have not tested location queries. |

### C3 – Changes in data can be subscribed to

| Req. | What it says | Status | What we do, and what is missing |
|---|---|---|---|
| R3.1 | Systems for use cases that require notifications provide at least one mechanism to receive updates on data changes. | **Not applicable** | The requirement is conditional. Our use case is a modelled day delivered in a batch and then analysed, so nobody needs a notification. The context broker (Orion-LD) supports NGSI-LD subscriptions, but we do not use or expose them. If a use case needed notifications we would have to add and test them. |
| R3.2 | (*may*) Several subscription mechanisms. | Not applicable | As above. |

### C4 – Access to information can be restricted
No numbered requirement. If access is restricted, the restriction follows MIM3 and MIM6.

| What | Status | What we do |
|---|---|---|
| Restrictions follow MIM6 | **Followed** | See [MIM6](mim6-securing-data.md): ODRL policies, approval by the data rights holder, an agreement check at every use, and credentials checked by DCP. |
| Restrictions follow MIM3 (identification of the parties, RC5.2 to RC5.4) | **Followed** | See [MIM3](mim3-exchanging-data.md). MIM3 is followed, and the part MIM0 relies on, identifying and checking the parties (RC5.2 to RC5.4), is met. MIM0 does not name the MIM3 requirements it means; this is our reading. |

A note on the specification: MIM0 refers to "MIM6.C1.R4" for authorisation and actor roles. We found no R4 in the v9.0 text of MIM6, where the closest requirement is R1.3 (access rights). We take it as a reference that was not updated, and ask readers who know better to correct us.

## Recommendations that are not requirements (best practices)

| Recommendation | Where we stand |
|---|---|
| Current data | Yes (the open view). |
| Historical data | Yes (the time series interface). |
| Geospatial querying (MIM7) | Not for B, by design (no positions). |
| Subscriptions when applicable | Not applicable (see R3.1). |
| Next expected update | No. A batch is produced when someone starts it, so there is no schedule to report. |
| Explicit endpoint versioning | The NGSI-LD interface is versioned (`/ngsi-ld/v1`). Our own open view is not versioned. |
| Example payloads or test queries | Yes: `docs/07-folj-ett-varde.md` shows real responses, and the open view links an example query. |
| Standard caching headers | Not on the data. The draft data model pages send `Cache-Control: no-cache` on purpose, because they change. |
| Rate-limit status in standard headers | Partly: a refused request gets `429` with `Retry-After`. No headers on accepted requests. |
| Structured error bodies | Yes: JSON `{"fel": "..."}` on the open view and the ETSI problem details from the time series interface. |
| Partial responses or projections | Yes (`attrs` on the time series interface). |
| A health or status endpoint | Yes (`/health`). |

## PoC limitations
None of the requirements above is held back only because Svada-mini is a PoC. The open data on the public demo is reset every night, so a time series is
short and a chamber list can be empty right after a reset. That does not change how the interface works.

## Svenska (sammanfattning)
**Vårt påstående: Svada-mini följer MIM0 (egen bedömning). Inget krav har statusen "Följs inte". R3.1 (prenumeration) gäller inte vårt användningsfall.**
Data går att hämta maskinläsbart (JSON eller NGSI-LD, med innehållsförhandling), via standardwebb (HTTPS, REST, NGSI-LD) och med formell beskrivning (OpenAPI för
den öppna vyn, ETSI-standarden för tidsserien). Gränssnittet är strukturerat och går att fråga med tid och attribut. Positionsfrågor erbjuds inte för B eftersom B
saknar positioner med flit. Åtkomstbegränsning följer MIM6; MIM3 följs, och den del MIM0 bygger på, identifieringen av parterna, uppfylls. Datamodellerna (R1.4) är specificerade i prosa och OpenAPI; utkastet till modell publiceras också maskinläsbart (JSON Schema, JSON-LD-kontext och termlista) på /modell, och det hör till MIM2 (vars R1 vi följer). Vi redovisar också rekommendationerna som inte är krav.
